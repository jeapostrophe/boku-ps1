# Event scripts — the VM, triggers, voice keys and scene flow graphs (PLAN `REC-05`)

Measured on the dump identified in [disc-recon.md](disc-recon.md) unless marked *hypothesis*.
RAM addresses are in `SCPS_100.88`; symbol names are ours. The event block's container layout
and the text words are in [text-format.md](text-format.md); members and `g_cd_dir` in
[boku-bin.md](boku-bin.md). The per-event inventory is [`data/scenes.tsv`](data/scenes.tsv) and
the graph is [`data/scene-edges.tsv`](data/scene-edges.tsv), both regenerated by
`python3 work/rec05/scenes.py` (stdlib; `--report` prints every number quoted here,
`--selftest` breaks the decoder on purpose, `--dump <ids>` writes decoded scenes under `work/`).
Neither TSV contains text: ids, numbers, our speaker names and symbolic conditions only.

## Summary

* 677 events, every one with bytecode; **36 opcodes in use out of a 40-entry table**; the walker
  decodes all 677 with no desync, every jump lands on an instruction, `END` is always last.
* The opcode numbering is the PS2 sequel's list (Hilltop, [related-projects.md](related-projects.md)
  § 2) with `CMAP`, `CMAPP`, `CMWT` and everything after `XSEEK` absent. That list was a
  hypothesis; the handlers read here agree with it name for name (`MOVIE` queues a movie,
  `LFLAG` writes another event's local flag, `WARP` sets an actor position, `XSEEK` pre-seeks
  the next voice…).
* **Control flow is three opcodes**: `JMP`, `JMPM` (current map == name), `JMPE` (flag ≥ value).
  `SELECT` does not branch; it writes the chosen index to `g_flags[255]` and `JMPE` tests it.
* **Every one of the 2,686 text entries is reachable.** 2,603 through bytecode from the event's
  entry; 83 are opened by two native routines (the dinner quiz) by a day-computed index. No
  dead text.
* An event fires when (a) its map variant is loaded, (b) **its id says which day** (`id / 100` =
  day 1…31 for ids below 4000), (c) its entry-1 condition tree holds (hour, day, flags, map),
  and (d) its placement record's trigger happens (auto on map entry / talk to character *k* /
  examine a spot / walk into a zone).
* The 12-byte voice key is `{u32 first sector, u32 end sector, u8 channel, u8 file, u16 0}`
  inside `BOKU_XA.XAM` — checked against the image's XA subheaders, 2,163 of 2,163.
* The speaking character is an operand of `XAMSG`/`XA` and agrees with the inline label in all
  but 11 of 2,487 voiced lines.

## Bytecode

Entry 2 of the block. An instruction is `u8 opcode, u8 size, operands…`; `size` counts 16-bit
words including the two header bytes, so the next instruction is at `pc + 2·size`. The
interpreter advances by the size byte (every handler ends `pc + 2·pc[1]`) and breaks into the
debugger on a zero size (Shift-JIS `printf` "構造体のサイズが０" — "struct size is 0" — at
`0x80029D94`, then `break`).
Operands are little-endian; "`@n`" below is the byte offset from the instruction start.
Code ends with `END`; 0 or 2 bytes of uninitialised pad follow.

`ev_run` (`0x8002D23C`, called once per frame from `0x80019798`) loops: fetch at `g_ev_pc`
(`*0x80036340`), call `g_ev_ops[opcode](pc, &status)` (`0x80029014`, 40 pointers, `jalr` at
`0x8002D624`), store the returned pc; `status` 0 = continue this frame, 1 = yield (handler
returned its own pc to be re-run next frame), −1 = event over. **Opcodes 0–2 are skipped by
`ev_run`** — they belong to the init pass.

`ev_init(block, placement)` (`0x8002D6D8`) runs when a map is entered, for every event whose
condition holds: it walks the code from the top to `END` executing **only opcodes 0–5** (`POS`,
`IPROG`, the three jumps) and skipping the rest by size. So actor placement is conditional on
the same jumps the scene uses, and a `JMPE` on a flag is evaluated twice — at map entry and
when the scene runs. `ev_peek_voice` (`0x8002D7FC`, used by `XSEEK`) walks the same way until
the next `XAMSG`/`XA`/`END`.

**The gate can fail.** The walker advances by the table above, not by the size byte, and
requires the two to agree, the walk to end exactly on `END`, < 4 bytes to follow, every jump to
land on an instruction, and every message operand to be in range. `--selftest`: `ANM` mis-sized
as 2 words → 599 events fail; `WAT` as 3 → 606; `SELECT` as 4 → 26; `JMPE` as 3 → 290; `YGO`
dropped from the table → 2.

### Flags — what a script can test

`flag_get(id)` `0x8003119C` / `flag_set(id, v)` `0x800311D8`:

* `id ≥ 0` — **global flag** byte `g_flags[id]` (`0x80035E48`, 256 bytes). 168 distinct flags
  are tested and 169 set by scripts. Values are small counters, not just booleans.
* `id < 0` (always written `−1`) — the event's **local flag**: one byte per (map base, event
  id), in `g_lflags` (`0x80035C48`, 64 × `{char map[3], pad, s16 event, u8 value, pad}`;
  `lflag_get` `0x80030E50`, `lflag_set` `0x80030F14`, `lflag_set_for` `0x80031014`). This is the
  "how many times has this scene played" counter: the usual shape is `JMPE lflag ≥ 1 → short
  repeat line`, else `FLAG lflag = 1` and the full scene.
* `g_flags[255]` (`0x80035F47`) is the **result register**: `SELECT` writes the choice, `PROG 4`
  the day, `PROG 12` the hour, `PROG 6` which side Boku approached from (0–3, picks the turn
  animation), `PROG 14` a byte from `0x80025914` (*unknown*). `data/scene-edges.tsv` names it
  `choice`, `day`, `hour`, `side` when an event has one kind of writer, else `R`.
* `g_flags[1]` receives the dinner-quiz result (below).

There is **no random branch and no item/insect-count test in bytecode**: a script can test only
flags, the map, and whatever a `PROG` copies into `R`. Conditions on day and hour live in the
event's condition tree (below) or come through `PROG 4`/`12`.

## Entry 0 — the cast to preload

`u32 n; n × {u8 slot, u8 variant}`, padded to 4. The models the event needs, as
`H_<slot>_<variant>` in `H_FILES` ([boku-bin.md](boku-bin.md)). Of 1,103 `POS` instructions 999
name a pair listed here, 98 are `(0, 0)` — Boku's default model, always resident — and 6 are
others (*hypothesis:* loaded by a sibling event of the same map). Not needed for translation
beyond confirming that **slot = character**.

## Entry 1 — the condition tree

`u32 len` (0 = unconditional, 78 events), then `len` bytes of 8-byte nodes, the root first,
children inline after their parent. Evaluated by `ev_cond` (`0x80030784`) →
`cond_group` (`0x800305F4`) → `cond_cmp` (`0x8003041C`).

| byte | field |
|---|---|
| 0 | kind: 0 = AND group, 1 = OR group, 8 = map, 9 = flag, 10 = hour, 11 = day (2–7 exist in the switch table `0x80029E68` and do nothing) |
| 1 | flag id (kind 9) |
| 2 | comparison: 2 `==`, 3 `!=`, 4 `>`, 5 `>=`, 6 `<`, 7 `<=` (table `0x80029E50`) |
| 3 | group: child count · flag: 1 = global flag `byte 1`, **0 = the event's local flag** |
| 4… | value (`u8`); for kind 8 a 3-character map base, compared with the current map's first 3 characters |

599 events have a tree: 507 hour tests, 386 day tests, 519 flag tests, 33 map tests. The same
node format is used by `EVVER.BIN` (below), which cross-checks the parser.

**The event id is part of the condition.** `ev_cond` splits `id = 100·dd + nn`:

* `1 ≤ dd ≤ 39` and the tree has no day node → the event requires **`day == dd`**. 362 events
  are day-keyed this way (7–27 per day; day 1: 27, day 31: 2); the other 131 ids in that band
  carry their own day node (a range, or several days).
* In map `G02` only (the room where meals are taken), for `dd < 40`, `id ≥ 5`: `nn == 1` (or id
  6) requires the clock to read exactly **07:00**, `nn == 2` (id 7) **08:00**, `nn == 3` (id 9)
  **18:00**, `nn == 4` (ids 10, 705) **19:00**, and records the id in `g_clock.meal[0…3]` so
  only one event per slot fires per day. 13 / 20 / 13 / 25 events carry those suffixes.
* Id bands: `0001–0099` 11 events (every-day routines), `0101–3199` 493, `4xxx` 63, `5xxx`
  51, `6xxx` 12, `7xxx` 1, `8xxx` 46 — not day-keyed; gated by flags.

`g_clock` is `0x80028FA0`: `{u8 day, u8 hour, u8 minute, u8, char *map_name, s16 meal[4]}`. Day
1…31 is the date in August.

### Map names and `EVVER.BIN`

A map file is `M_` + **base** (letter + 2 digits) + **time slot** + **2-digit variant**.
`map_variant_name` (`0x80030CD0`) builds it from the base: the 4th character is `0` for hour <
16 (< 15 outside bases `H19`/`H26`), `1` until 18, `2` from 19 (`0x80030A64`); the variant comes
from `EVVER.BIN` (resident at `*0x800278E8`): `u32 off[9]` for base letters `A`…`I`, each
`u32 n; u32 off[n]` of records

`{char base[4]; u32 days; char slots[4]; char variant[4]; [condition tree if days bit 31]}`

— `days` bit `d−1` = valid on day `d`, `slots` = the time-slot digits it applies to. First
match wins, default `00`. 132 records; e.g. `G02` has five breakfast variants
(`hour < 8`, by day), eleven dinner variants (`hour == 18`), `H06`/`H08` switch permanently on
day 16. So **each copy of an event sits in the map variants — place, time slot, days — where it
can fire**, and `data/scenes.tsv` lists them. Letters by event count: `G` 319, `H` 179, `A` 121,
`I` 49, `D` 39, `B` 35, `C` 20, `E` 5; busiest bases `G02` 80, `A18` 64, `G01` 54, `G06` 41.
`I` maps are single-event close-ups entered by `MAP` from another event and left the same way.
*What place each base is has not been established* — nothing in the data names them.

## Voice key

Entry `3 + 2i`, 12 bytes, consumed by `xa_play` (`0x8002B3E4`): `CdlPause`, position from
`start` (through `0x8005246C`, which adds the XAM file's position), `CdlSetfilter {file,
channel}`, `CdlReadS`.

| offset | field | measured |
|---|---|---|
| 0 | `u32 start` — sector **relative to `BOKU_XA.XAM`** | 0…89,932 of 96,453; `start % 16 == channel` in 2,602 of 2,602 |
| 4 | `u32 end` — sector of the same channel where the clip stops | `(end − start) % 16 == 0` always; median clip 416 sectors (26 of its own); 3 keys have `end == start` |
| 8 | `u8 channel` | 0…15 |
| 9 | `u8 file` | 2 or 3 |
| 10 | `u16` | 0 |

Checked against `disc/image.img`: the XA subheader at both `start` and `end` carries the key's
file and channel for all 2,163 distinct keys. The stream is 16-way interleaved with file
numbers 2 and 3 alternating by region. A reinserter copies keys verbatim; nothing in a key
depends on text.

## Building the flow graph

Nodes: `XAMSG`/`MSG`/`XA`/`SELECT` instructions (id `E<event>.<msg>@<pc>` — a message shown
from two places is two nodes), the native `PROG 15`/`16` (`.P15@pc`), and `MAP`/`MOVIE`
(`.MAP:<base>[>E<next>]@pc`) so a chain is attached to the path that takes it. `ENTRY` and `END`
are per event. Edges: from each node, walk the non-node instructions to the next nodes,
collecting branch conditions.

* A `SELECT`'s out-edges are computed once per option (`opt0…`, `cancel`) with `R` bound to
  that value, so `JMPE R` is decided rather than reported.
* A path remembers constants it assigned (`FLAG lflag = 1`), so a later test of that flag is
  decided; a variable overwritten with an unknown value is primed (`R'`) from there on.
  Infeasible paths are dropped, alternatives that differ only by a covering split are merged.
* One event (`E4032`) has too many independent tests to enumerate; its edges carry `*`
  ("under some flag condition — read the bytecode") for everything but `R` and `lflag`.
* Play order in `scenes.tsv` is depth-first from the entry, fall-through before jump target.

Totals, reachable from entry: 2,718 text nodes (2,465 `XAMSG`, 114 `MSG`, 115 `XA`, 24
`SELECT`), 5 native nodes, 270 `MAP`/`MOVIE` nodes, 762 conditional branches,
3,284 node-to-node edges + 977 entry edges; 9 of 85 `SELECT`s are cancellable. In use:
`1.1`/`2.1` yes-no (14), `3.x`/`4.3` three-way; most three-way selects are the 61 quiz tables.

**Continuation messages** (text-format.md § Duplication) are simply the next `XAMSG` on the
same path; the graph orders them.

## How events chain, and the shape of a day

* There is **no call opcode**. An event hands over with `MAP base, event` or `MOVIE base,
  event, n`: at `END` the map changes and the named event auto-starts. 71 reachable hand-overs;
  **69 name the event itself** — the scene continues in another map (a close-up `I` map, or
  after an FMV) and uses `JMPM` + its local flag to find its place; `LFLAG` pre-sets the local
  flag for the destination map. Only 2 name a different event.
* Everything else is sequenced by **state, not by calls**: an event sets global flags and the
  clock (`TIME`), and the next event's id (day), condition tree (hour, flags) and meal slot
  make it eligible. The day, as the `G02` events show it: 07:00 `dd01` talk at the breakfast
  table → 08:00 `dd02` after breakfast (opens with the shared `0007_xx` "gochisōsama" lines) →
  free roaming, `talk`/`examine` events gated by hour bands and flags → 18:00 `dd03` dinner
  talk → 19:00 `dd04` after dinner (shared `0010_xx` lines) → night maps → bed (the diary is
  `ZUKAN.OVL`, not bytecode). The aunt's "guess tonight's dinner" quiz is `PROG 15` (events
  `0221`, `1502`, `3023`); `4028`/`4064` announce the menu (`PROG 16`).
* Most-tested global flags — candidates for story progress: 72 (31 tests), 30 (23; the
  beetle-sumo trees), 251, 248, 81, 131, 10, 172, 83, 79, 84, 21, 55, 25. Most-set: 251, 248,
  131, 228, 239, 172. *Their meanings are not established.*
