# How the game stores its text (PLAN `REC-03`, text half of `REC-02`)

Measured on the dump identified in [disc-recon.md](disc-recon.md) unless marked *hypothesis*.
RAM addresses are in `SCPS_100.88` (file offset = RAM − `0x8000F800`); symbol names are ours.
Containers, the `.SEC` indexes and `g_cd_dir` are in [boku-bin.md](boku-bin.md); the font and
the id → cell formula are in [font.md](font.md). One row per physical text site is in
[`data/text-sites.tsv`](data/text-sites.tsv), regenerated by
`python3 work/rec03/text_sites.py` (stdlib; `--report` prints every number quoted here,
`--selftest` breaks each gate on purpose, `--dump` writes a decoded script under `work/`).

## Summary

* All dialogue lives in **event blocks**. A block is one event (script + voice keys + text);
  it is addressed by a 16-bit **event id**. A block sits in the map packs where it can fire
  (`M_FILES.BIN`, child 1) and/or in `EV.BIN`. **The same event is copied, byte-identical in
  its text, into every map variant that needs it** — that is the whole duplication model.
* Everything else (item names, descriptions, system and memory-card messages, the insect
  book, menus) is **`u16` arrays compiled into the executable and four overlays**, reached by
  `lui`/`addiu` and an item index.
* **6,183 physical sites = 2,977 logical lines** (2,686 event lines + 291 array lines),
  2,426 distinct byte strings, 74,584 glyphs in logical lines (160,084 physical).
* Only three control words occur in the whole game: `0x8000`, `0x8001`, `0x8002 <u16>`.

## Text words

Little-endian `u16`. Bit 15 clear = glyph id (0…1487 in use; 0 is the blank cell). Bit 15 set =
control; **the renderer switches on the low byte only** (`dialog_draw` `0x8002BDA8`):

| word | count in text | meaning (measured in `dialog_draw`) |
|---|---:|---|
| `0x8000` | 5,698 | end. Sets "done" in `g_dialog.flags` (`0x800359E4`). |
| `0x8001` | 7,472 | newline. Dialogue is **vertical**: `x -= 14`, `y = y0`. (In the horizontal mode of the same routine: `x = x0`, `y += 13`.) |
| `0x8002, p` | 1,978 | page break. Stops drawing, remembers the address after `p` as the next page; if the line is voiced, `p` is loaded into a frame countdown (`0x800359F4`) that turns the page by itself (`dialog_next_page` `0x8002BD8C`). `p` is 21…270, a multiple of 3 in 1,936 of 1,978. Occurs **only in voiced messages**. |
| other `0x80xx` | 0 | skipped without drawing. None exist in the data. |

`0xFFFF`, `0xCDCD` and any word ≥ `0x8003` never occur inside text. There are no colour,
name-substitution or choice-marker codes; choices are a separate site kind (below).

**Kendrit's page guard, on PS1.** The PSP sequence `0x8002, p, 0x0000, <next page>` holds in
the data 1,978 times out of 1,978. But `0x0000` is not a guard here: `dialog_draw` resumes
the next page *at* that word and hands it to `glyph_draw` (`0x8002BA2C`) like any glyph — id 0
is the blank cell. The same blank follows **every** `0x8001` inside a message (6,010 of 6,010):
it is the authoring tool's one-cell indent of continuation columns under the `speaker「`
opening. Deleting it un-indents; it does not eat a character (*measured from code; not yet
confirmed on screen*). A reinserter must still treat `0x0000` as a glyph, never as a terminator.

Other readers, all of which treat *any* bit-15 word as a line end and never look for a
`0x8002` parameter: `select_draw` (`0x8002C234`, vertical, 12 px step), `text_draw_h`
(`0x80043864`, horizontal, advance 12, line step 16), `text_nth` (`0x800438F0`, skips *n*
`0x8000` words), `text_nth_line` (`0x8003532C`, skips *n* bit-15 words), and the inline walker
in `sysmsg_draw` (~`0x80037A3C`).

Layout limits observed in messages: at most **3 columns per page and 16 glyphs per column**
(50 columns are exactly 16). Dialogue opens at (297, 22) via `dialog_open` (`0x8002BD30`).

## Event block

Used unchanged in three places: each table of a map pack's child 1, each `EV.BIN` member, and
three blocks resident in the executable.

| offset | field | |
|---|---|---|
| 0 | `u32 n` | entry count: 2, or odd ≥ 3 |
| 4 | `u32 off[n]` | from block start; ascending; `off[0] == 4 + 4n`; 0 = null entry |
| `off[0]` | header | 4–24 bytes, not decoded |
| `off[1]` | trigger/actor data | has its own internal offsets (relative to itself); not decoded |
| `off[2]` | bytecode | `u8 opcode, u8 size_in_words, args…`; ends with opcode `0x15` and a zero word when needed for 4-alignment. Each of the 36 opcodes in use has one fixed size (opcode 0 also appears as that zero pad). |
| `off[3+2i]` | key *i* | 12 bytes `{u32 start, u32 end, u32 flags}` — the voice clip; null if unvoiced. *Hypothesis:* XA position, low nibble of `start` = channel (it repeats in `flags`). |
| `off[4+2i]` | text *i* | the message; null if the entry is voice-only |

`n == 2` is a **stub** (455 of the 2,087 map blocks): header and trigger data only. Every stub's
id is an `EV.BIN` member, which holds the full event and is loaded on demand by `event_select`
(`0x80019D2C`).

So the PSP/PS2 "first three entries are not text" holds exactly; the PSP's ASCII name entries
are 12-byte voice keys on PS1.

**Messages are addressed by index, from bytecode, within the current block**
(`g_ev_block` `*0x80036338`; key offset at `block + 0x10 + 8i`, text offset at `+0x14 + 8i`):

| opcode | size | args (byte 2…) | handler | |
|---|---|---|---|---|
| `0x0D` XAMSG | 4 | `a, b, msg, c, d` | `0x8002F458` | start voice of key `msg` (`0x8002CF14`) and open text `msg` (`0x8002CF9C`) |
| `0x0E` MSG | 4 | `…, msg, …` | `0x8002F524` | open text `msg` only — 585 sites, all unvoiced |
| `0x0F` XA | 4 | `…, msg, …` | `0x8002F588` | voice only — all 446 null-text entries (stored copies of 115 distinct messages, [voice-only.md](voice-only.md)) are named by this and nothing else; `VO-02` gives one text ([event-scripts.md](event-scripts.md) § Voice-only entries) |
| `0x21` SELECT | 3 | `type, variant, msg, d` | `0x80030058` | `select_open(msg, type, variant, d)` `0x8002D00C` |

The dispatch table is `g_ev_ops` at `0x80029014` (40 handlers, `jalr` at `0x8002D624`). Native
code also opens messages by computed index (`0x800318EC`: `msg = table[…] + 7`;
`0x80031858`: `select_open(s0 + 1, 4, 2)`), but in the shipped data every text entry is named
by at least one of the four opcodes.

**Two kinds of text entry**, decided by the opcode that names it:

* **MSG** (5,574 sites): runs to the first `0x8000` (skipping `0x8002` parameters).
* **SELECT** (319 sites): **no `0x8000`**. It is `L` lines each ended by `0x8001` — prompt lines
  first, then the options — and `L` comes from the executable, not the data:
  `L = g_select_lines[g_select_base[type-1] + variant-1]` (`0x80028F74`, `0x80028F6C`;
  `g_select_first` at `0x80028F80` gives the number of leading prompt lines). In use: 1.1 → 2,
  2.1 → 2, 2.2 → 4, 3.1 → 3, 3.2 → 5, 3.3 → 3, 4.3 → 3. A translation may change line lengths,
  never the line count.

After a text the entry is padded to 4 bytes: 0 or 2 bytes (3,011 / 2,881). **The pad is
uninitialised build-tool memory** — 339 distinct values, 1,099 zero, never `0xCDCD`. Nothing
reads it. Block lengths are all multiples of 4.

### Map pack child 1

`u32 n_blocks; n × {u16 event_id, u16 length, u32 offset}` then the blocks. `offset` is from the
start of child 1, `length` is the block's byte length, blocks chain exactly (`offset[i+1] ==
offset[i] + length[i]`, last end == child size) in all 555 maps. Ids are **not** sorted and
**can repeat inside one child** (17 cases, up to 4 copies, always byte-identical). Largest block 6,136 bytes
(`u16` ceiling 65,535); largest child 1 is 11,992 bytes.

Sibling children do not point into child 1. Child 0 contains 79 % of its map's event ids as
`u16` values and child-1 offsets only at chance level (2–3 %, same as children 2, 4, 5):
*hypothesis from statistics* — events are placed by id, and the block is found by walking the
child-1 table.

### `EV.BIN` member

One bare block, no wrapper; the id is `EV.SEC`'s `event_id`. 265 members, 250 with text.
Every `EV` id also appears in at least one map's child 1: 226 ids only as stubs, 10 only as
full copies, 29 as a stub in some maps and a full copy in others. A full map copy of an `EV`
id is always byte-identical to the `EV` member (93 of 93).

### Blocks in the executable

`0x80029920` (5 entries — one voiced message, the "playtime is over" call), `0x80029A40`,
`0x80029A8C` (3 entries, no text). Chosen by `0x80019DEC` for system events 8 / `0xFD7` /
other. No length field; nothing follows them that depends on their size except the next symbol.

## Text arrays in code files

C `u16` arrays, 4-aligned with a `0x0000` pad word where needed. Three shapes: **E** — items
ended by `0x8000`, item *k* found with `text_nth`; **L** — every bit-15 word ends a line and
code passes a line index; **S** — a short select/line group drawn whole. All overlays load at
`0x80079A08`: with that base `HHON.OVL`'s two `lui`/`addiu` references land exactly on its first
string (`+0x5328`) and its select (`+0x6874`), and `jal`s into each overlay land on an
`addiu sp` in 54–100 % of cases (*the base is a hypothesis for `ZUKAN`/`TAKO`/`MUSI`*).

| file | RAM / file offset | shape | items | referenced from | content |
|---|---|---|---:|---|---|
| EXE | `0x80029AFC` | E | 1 | `0x80032048` | ant-count message. **Code overwrites words 1–3 with digits** (`0x34 + d`, `sh` at `0x80032058…84`) |
| EXE | `0x80029B20`–`0x80029C40` | L | 22 | `0x80035414`, `0x80035464` | controls help; uses the highest ids (1479–1487, button icons *hypothesis*) |
| EXE | `0x8003D2E0`–`0x8003DA66` | L | 103 | `0x80037C84` | 60 insect names, memory-card and system messages, menu words |
| EXE | `0x80046158`, `0x80046178`, `0x800461BC` | S | 3 | `0x8003F1D0`, `0x8003F0A4`, `0x8003F020` | insect-cage selects |
| EXE | `0x800461CC` | E | 8 | `0x80042064` | kite names |
| EXE | `0x80046214` | E | 15 | `0x80041780` | item names |
| EXE | `0x800462C8` … `0x80046390` | E/S | 9 | `0x80043EF8`–`0x80043FE4` (one `addiu` each) | fishing screen |
| EXE | `0x80046398` | E | 13 | `0x800417F4` | item descriptions |
| EXE | `0x80046614`–`0x80046972` | E | 19 | `0x80041840` | photo and morning-glory captions |
| `HHON.OVL` | `+0x5328` | E | 61 | `0x8007B47C`, `0x8007B598` | insect book entries (index 60 = empty slot) |
| `HHON.OVL` | `+0x6874` | S | 1 | `0x8007D230` | select |
| `ZUKAN.OVL` | `+0x32E8` | S | 1 | not traced | "write the diary and sleep?" select |
| `TAKO.OVL` | `+0x4` | S | 1 | not traced | kite menu |
| `MUSI.OVL` | `+0x4`, `+0x2C` | S, L | 1 + 32 | not traced | release select; bug-sumo move names |

`TITLE.OVL`, `BUMPER.OVL`, `ENDOTI.OVL` hold no glyph text (TITLE draws digits as
`glyph_draw(0x34 + d)` — **the digit glyphs' ids are constants in code**, as in the ant message).

## Reconciliation — the gate

Structural walk vs. `REC-01`'s heuristic scan of `BOKU.BIN` (5,553 hits), both directions:

| scan hit | count |
|---|---:|
| ends on a structural site's `0x8000`, same start | 1,855 |
| … scan started late (it stops at glyph 0 and at ids > `0x4FF`) | 3,617 |
| … scan overran backwards into the preceding key/bytecode | 46 |
| not structural, inside a TIM's extent | 30 |
| not structural, 3-glyph runs in model/other data (`H_01_04.BIN` ×3, `SMI05.BIN` ×2), judged noise on decode | 5 |

All 18 "stragglers" (`T_CONFIG`, `MI*`, `SUB.BIN/.TIM`, `DAMMY*`, `MZ`, …) and the 17 hits in
map child 6 are in that noise. Of 5,989 structural sites in `BOKU.BIN`, 5,518 were seen; the
471 missed are 355 with no `0x8000` (selects, line lists) and 116 with fewer than 3
scan-visible glyphs before the end. None unexplained. For the executable and overlays an
END-anchored scan (glyph 0 allowed, ids ≤ `0x5FF`) gives 129 hits, 120 structural; the 9 others
are in `SCPS_100.88` at file `0x15C2C`, `0x15E2C` (data), `0x1A15C`, `0x1A27E` (bytecode of the
resident blocks), `0x60C8A`…`0x60E9A` (data) — gibberish on decode. Arrays without `0x8000`
were found by a kana-run scan and by their code references; *that half is not gated*.

The gate can fail, and did: it rejected a kite-name array end typed 2 bytes short ("E array
not END-terminated"); the first reconciliation showed 45 hits outside every site, which were
the scan overrunning, not missing text; and with opcode `0x0E` unknown it reports 585
messages named by no opcode. `--selftest` reproduces three such breaks (585 / 305 / 2 problems).

## Duplication and line identity

* 2,352 block instances carry **677 distinct event ids**; 535 ids have text (285 only in maps,
  215 only in `EV.BIN`, 35 in both).
* **For every (event id, message index), all copies are byte-identical: 0 conflicts in 2,686.**
  Copies per logical line: 1× 1,792 · 2× 689 · 3× 163 · 4–7× 236 · 8–26× 97 (max 26).
* Copies exist because map variants (`M_A04000` / `M_A04001` / `M_A04100` — time of day, day
  state) each embed the events that can fire there.
* 246 byte strings are shared by more than one logical id (yes/no selects, repeated system
  lines, tutorial text under three event ids). They stay separate lines — context differs —
  and are translation-memory candidates.
* Some messages are continuations of the previous one (they start with the indent glyph and
  close a bracket the previous message opened); scene order is `REC-05`'s.

**Proposed line id (`PIPE-01`).** Event text: `E<event id>.<message index>`, e.g. `E0607.1` —
it names the logical line once, and its sites are every block instance with that id. Array
text: `<file>@<original offset>.<item>`, e.g. `exe@80046214.3`, `hhon@5328.12`. Both are read
off the *original* disc, so they are identical on every machine and unaffected by edits; the
import step must assert the zero-conflict invariant above and fail loudly otherwise.

## What a reinserter rewrites when one line grows by N bytes

Inside a block (map or `EV`), for **every** physical copy of the logical line:

1. the text, then a 0/2-byte pad to 4 (value free);
2. `off[]` of every later entry of the block;
3. *map:* this block's `length` and every later block's `offset` in the child-1 table;
   *`EV`:* nothing at this level;
4. *map:* child 1's `size` and the `offset` of children 2…6 in the pack table (null `{0,0}`
   entries stay null; children are 4-aligned);
5. the member's `size` in `M_FILES.SEC` (`u32`) / `EV.SEC` (**`u16`**, largest now 3,812);
6. only if the member crosses a sector boundary: `sector` (`u16`) of every later `.SEC` record,
   then `g_cd_dir_size` of the container and `g_cd_dir_lba` of everything after it
   ([boku-bin.md](boku-bin.md) § "The directory in the executable").

Not rewritten: bytecode (messages are indexed, jumps stay inside the code entry, which precedes
all text), voice keys, entry 1's internal offsets, sibling children (*hypothesis*, above),
select line counts.

Slack that avoids step 6 — free bytes to the sector end, per text-bearing member (636): min 16,
p10 368, median 1,246, p90 1,784, max 2,044; 10 members have < 64 (`M_A10101` 16, `M_G06003`
24, `M_G12201` 24, `M_A18102` 32, `M_I30000` 32, …). Text is 260,064 bytes in maps, 84,050 in
`EV`, 10,224 in arrays.

Arrays in code files have **no slack**: an array is followed by the next symbol. Growth means
relocating the array and patching the `lui`/`addiu` pair(s) in the table above; **L** and
**E** arrays must keep their item count and order (code holds the indices); the ant message
must keep three digit cells where the code writes them, or the code changes too.

## Glyph ids in use

1,328 distinct ids, 0…1487, 160 unused below the maximum. 415 ids ≥ 1024 (2,674 uses, 1,399
sites): they are the tail of the same single sheet — rarer kanji in order of first need, not a
second page ([font.md](font.md)). Use is steeply front-loaded: ids 0–251 carry 128,776 of
160,084 glyphs; 1260–1487 carry 777. Full histogram: `work/rec03/glyph-hist.tsv` (local).
