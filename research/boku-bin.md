# `BOKU.BIN` — the archive, its directory, and its member map (PLAN `REC-01`)

Everything here was measured on the dump identified in [disc-recon.md](disc-recon.md) unless it
is marked *hypothesis*. Addresses are RAM addresses in `SCPS_100.88` (file offset = RAM −
`0x8000F800`); symbol names are ours. The member map itself is
[`data/boku-bin-members.tsv`](data/boku-bin-members.tsv), regenerated by
`python3 work/rec01/build_map.py` (stdlib only; `--report` prints every check quoted below).

## What `BOKU.BIN` is

`BOKU.BIN` is **a raw copy of a sector range of the developers' CD image**: the `\_DATA`
directory's own 9 sectors, then the 275 files of `\_DATA` in ISO 9660 (alphabetical) order, each
padded to a sector, then the 1 sector of the `\__STR` directory. The two directory extents were
zeroed; they are the 9 leading zero sectors and the final zero sector. Nothing inside the
archive says where anything is. The directory is compiled into the executable as **absolute
disc LBAs**, which work because the retail disc puts `BOKU.BIN` at the LBA (1046) where the
dev image had `\_DATA`.

## The directory in the executable

`g_cd_dir` at `0x80024698` (file `0x14E98`), immediately preceded by the three arrays it
points to:

| RAM | field | value |
|---|---|---|
| `0x80024698` | `u32 count` | 305 |
| `0x8002469C` | `u32 *lba` | `0x8002384C` — `g_cd_dir_lba[305]` |
| `0x800246A0` | `u32 *size` | `0x80023D10` — `g_cd_dir_size[305]` |
| `0x800246A4` | pointer | `NULL`. Read only by `0x80012DBC` (one caller, `0x80012E40`, itself uncalled) — dead |
| `0x800246A8` | `char **name` | `0x800241D4` — `g_cd_dir_name[305]` |
| `0x800246AC` | `u32` | 0; tested at `0x800131A8` — purpose unknown |

Three **parallel arrays indexed by a file number**; there is no per-record struct and no third
per-file field — no flags, no decompressed size, no high bit. (`work/rec01/exe_dir.py` finds the
arrays from the count word.)

* `lba[i]` — absolute disc LBA. `cd_dir_pos` (`0x80012CFC`) passes it straight to
  `CdIntToPos` (`0x8004CAEC`, *name is a hypothesis from usage*) into `g_cd_loc` `0x80025A40`
  — the "last CD position" address psyouloveme's HUD script watches.
* `size[i]` — bytes. For the Form 2 files of `\__STR` it is `sectors × 2336`
  (`BOKU_XA.XAM`: 225,314,208 = 96,453 × 2336; ISO size 197,535,744 = 96,453 × 2048).
* `name[i]` — RAM pointer to a dev-time path (`\_DATA\MI00.BIN`). The strings sit at file
  `0x82C…0x1DF8` in *reverse* index order. Names are used only by the PC-host path and by
  name-search helpers that nothing calls (`cd_dir_search_file` `0x80012E84`, `cd_dir_find`
  `0x80012F84`, `0x80012FF8`). **The game addresses files by compile-time index constants.**

Index layout: 0 `\SCPS_100.88`, 1 `\SYSTEM.CNF`, 2 `\_DATA` (the directory, size `0x4800`),
3…277 the files of `\_DATA`, 278 `\__STR` (size `0x800`), 279 `BOKU_XA.XAM`, 280…304 the 25
`.IKI` movies. Indexes 2…278 are exactly `BOKU.BIN`, LBA 1046…54416.

### The table is the dev image's layout, and parts of it are stale

| entry | table | retail ISO 9660 |
|---|---|---|
| `\SCPS_100.88` | LBA 21, size `0x7F800` | LBA 23, size `0x80000` |
| `\SYSTEM.CNF` | LBA 1045 | LBA 279 |
| `M27`, `M28`, `M40`, `M60`, `M70` `.IKI` | alphabetical: 189980, 232420, 274410, 275530, 279200 | disc order `M40 M60 M70 M27 M28`: 195590, 238030, 189980, 191100, 194770 |
| everything in `\_DATA`, `BOKU_XA.XAM`, the other 20 movies | — | identical (checked against the image's directory records) |

The stale rows are harmless because those files are found through the real filesystem: the
movie player (`0x80034668`) calls `CdSearchFile` (`0x80050BDC`, *hypothesis from usage*) on the
name when the byte at `0x800295E8` is non-zero — it is `1` in the image and no `lui`-pair
write to it exists — and only otherwise uses `cd_dir_pos(index)`; the XA stream is opened by
`xa_init` (`0x8002AFB4`) via `iso_search_file` (`0x80013070`) on `\__STR\BOKU_XA.XAM;1`.
**`\_DATA` files are never looked up in ISO 9660** — they cannot be; the retail disc has no
`\_DATA`. Consequence for the reinserter: moving or growing a member means rewriting
`g_cd_dir_lba` / `g_cd_dir_size` in the executable, and nothing else at this level.

### Loader

| RAM | our name | what it does |
|---|---|---|
| `0x800129E0` | `file_load(s16 index, void *dst)` | 40 call sites. If `g_pc_host` (`u8 0x80023830`) → `PCload` of `C:\CD_IMAGE` + name (`pc_host_path` `0x800130A4`); else `cd_load_sync`. `g_pc_host` is `1` in the file and cleared by init at `0x80011FE4`. |
| `0x800127C8` | `cd_load_sync` | `n = (size+0x7FF)>>11`; each attempt first calls `0x800521FC` (clears the three libcd callback slots at `0x8004CD18`, resets libcd state, `DsEndReadySystem`), then `0x800506CC(cd_dir_pos(index), n, dst, 0x80)` (a `CdRead`-style call, mode `0x80` = double speed) and `0x80050A7C` (`CdReadSync`) until success. **The buffer is used as read: no decompression or fix-up step.** |
| `0x80012AB0` | `file_load_async` | 5 call sites; state machine `0x8001286C` / `0x800128AC` on the block at `0x80023834` (`s16 index, s16 state, …, void *dst`). |
| `0x80012D64` | `cd_dir_size` | 21 call sites; callers use it to bump-allocate the next buffer. |
| `0x80012DDC` / `0x80012E04` | `cd_dir_sectors` / `…_form2` | `(size+0x7FF)>>11`; `(size+0x91F)/2336` |
| `0x8001218C` | `boot_load_resident` | loads, by constant index, `BOKU_XA.XCH` 6, `ONMEM.BIN` 153, `EVVER.BIN` 31 (→ `0x800278E8`), `SUB.BIN` 224, `EV.SEC` 30 (→ `0x800278B0`), `M_FILES.SEC` 144 (→ `0x80026BD4`), `H_FILES.SEC` 44 (→ `0x80027568`), `MUSIDATA.BIN` 130, `FS00.BIN` 34, `MOV_VOL.BIN` 128, `MDLTIM.RTM` 53 |

The seven `.OVL` members are MIPS code loaded by the same `file_load` (`BUMPER` 8, `TITLE` 244,
`TAKO` 239, `MUSI` 129, `HHON` 42, `ZUKAN` 265, `ENDOTI` 28). `BUMPER` and `TITLE` load to the
address in the word at `0x80068AF4` (`0x80079A08` in the file); the other five sites were not
read.

## The four sub-archives and their `.SEC` indexes

Four big members are sector-granular sub-archives. Each has a small sibling **`.SEC`** ("sector
table") member that is its index; the `.SEC` files are loaded once at boot and stay resident.

| container (index) | index member (index) | record | records | key → dev name |
|---|---|---|---:|---|
| `EV.BIN` (29), 288 sectors | `EV.SEC` (30) | 6 B: `u16 event_id, u16 size, u16 sector` | 265 | `\..\EVT\BIN\EV%04d.BIN` |
| `H_FILES.BIN` (43), 2701 | `H_FILES.SEC` (44) | 8 B: `u8 id, u8 vr, u16 sector, u32 size` | 115 | `\..\MDL\DATA\BIN\H_%02d_%02d.BIN` (id, vr) |
| `M_FILES.BIN` (143), 41036 | `M_FILES.SEC` (144) | 16 B: `char name[8], u32 size, u16 sector, u16 junk` | 555 | `\..\MAP\BIN\M_%s.BIN` |
| `NIKKI.BIN` (149), 2162 | `NIKKI.SEC` (150) | 6 B: `u16 id, u16 size, u16 sector` | 94 | none in the EXE; the map calls them `NIKKI_%03d` |

Every `.SEC` starts with `u32 count`; `sector` is relative to the container's first sector;
`size` is bytes. `M_FILES.SEC`'s trailing `u16` is build-tool stack garbage (`"I4"`, `"ku"`,
`".B"` …) and is never read — the loader uses `lhu`.

**How a sub-file is loaded — the `.SEC` slot of the directory doubles as a virtual file.**
`map_select(name)` (`0x80017450`) walks the resident `M_FILES.SEC` comparing names
(`0x8004A7DC`), then writes `lba[144] = lba[143] + rec.sector`, `size[144] = rec.size`,
`name[144] = sprintf(0x800278B8, "\..\MAP\BIN\M_%s.BIN", name)` and the caller does
`file_load(144, buf)` (`map_load` `0x80017534`, async `0x8001756C`). `model_select(id, vr)`
(`0x80018620`) does the same with slots 43→44 and `event_select(id)` (`0x80019D2C`) with 29→30.
An unknown map name or model id is a `printf` + `break` — there is no fallback; an unknown
event id makes `event_select` return 0 ("NOT EVENT SEARCH %d"). `model_select` adds 50 to
`vr` when `id < 5` and bit `id` of a byte in the table at `0x80024B28` is set, which is why
`H_FILES` holds pairs like `H_02_03` / `H_02_53`. (The format strings are therefore live only on
the PC-host path.) The `NIKKI` reader was not located: `0x80043468` copies `lba[149]` to
`0x80048018` and nothing found by `lui`-pair scan reads it back — *hypothesis:* pointer-relative
access from the diary code. Its record layout is measured from data only (94 × 23-sector slots,
each a TIM of `0xB620` bytes, tiling `NIKKI.BIN` exactly).

**No second copy of the top-level directory exists inside the archive** (searched `BOKU.BIN`
for the LBA, relative-sector, byte-offset and size sequences as u16 and u32, and for any path
string: no hits beyond two coincidental u16 runs in geometry data). The `.SEC` members are the
only in-archive indexes, and the EXE holds no copy of them.

## The member map

`data/boku-bin-members.tsv`: 1302 leaf members = 2 directory placeholders + 267 plain top-level
members + 4 `.SEC` + 1029 sub-archive records (the four containers themselves are replaced by
their records). Columns: `dir_index`, `sub_index`, `name`, `offset`, `lba`, `size`, `sectors`,
`type` (guess), `signature` (recursive pack sniff), `entropy`, `zero_sectors`, `jpsxdec_tims`,
`text_lines`, `text_lines_only_here`, `notes`.

Validation (all from `build_map.py --report`):

* **Tiling is exact at both levels.** Every member starts where the previous one's last sector
  ends; top level covers 53,371 of 53,371 sectors; each `.SEC`'s records end exactly at its
  container's last sector. No gaps, no overlaps.
* **Slack is clean**: bytes between a member's `size` and its sector end are zero everywhere.
* **All 110 all-zero sectors are explained**: 9 `\_DATA` + 1 `\__STR` directory placeholders,
  and 100 that are ordinary data inside 100 members (74 in a map pack's background TIM, 17 in
  model data, 6 in other TIMs, 2 in overlay code, 1 in `DEMO_04.KEY`) — per-member in `notes`.
* **jPSXdec cross-check**: all 2,606 TIM positions in psyouloveme's `boku.idx` parse as a TIM
  whose whole extent lies inside one leaf member. Control: shifting every boundary by +1 / −1
  sector breaks 556 / 840 of them.
* **Packs chain**: `parse_pack` accepts only `first offset == 4+8n`, each offset == previous
  end (4-aligned), last end == blob end; `{0,0}` is a null entry (map-pack child 4, model
  slots). 880 members parse this way, recursively.

Type guesses (count): map pack 555 (always 7 children: 0 unknown, **1 event/message tables**, 2
unknown, 3 optional 98×79 8bpp TIM — 483 maps, matching jPSXdec's "483× 98×79" —, 4 optional,
5 unknown, 6 background TIM, 8bpp, 320×240 up to 720×240); event script 265 (an
offset-only table: `u32 n`, `n × u32` offsets from the table start); pack 187; TIM 134 (incl. the
94 diary pages); model pack 115 (`pack[2]{pack[N]{…}, blob}`); sound pack 22 (`.BGM`/`.SE`,
`ONMEM.BIN`, `M_S01000.BIN`); code overlay 7; sub-archive index 4; unknown 10 (`BOKU_XA.XCH`,
`DEMO_0x.KEY` — starts with a map name —, `EVVER.BIN`, `KAGO_UV.BIN`, `MOV_VOL.BIN` — magic
`MOV\0` —, `MUSIDATA.BIN`); pack of TIM 1.

**Sound is not VAB/SEQ.** `pBAV` and `pQES` occur nowhere. `.BGM` = `pack[3]{SShd, SSsq, body}`,
`.SE` = `pack[2]{SShd, body}`; the `SShd` / `SSsq` magic sits at +0xC of the child after
`{u32 head_size, u32 body_size, 0}`. No PsyQ TMD (`0x41`) or HMD (`0x50`) magic starts any member
or pack leaf — models are a house format.

## Compression: none

* The only loader is a raw `CdRead` into the destination; the map code then walks the pack in
  place (pointer arithmetic from `0x80017380` on). No decompressor is on the path.
* Entropy: no pack leaf ≥ 4 KiB exceeds 7.5 bits/byte; the highest whole members (7.6–7.7:
  `PK_ITM`, `PK_PHO`, `FISH01`) are packs of TIMs whose pixel-block lengths equal `w×h×2`
  exactly, i.e. raw. There is one `1F 8B 08` in 109 MB, unaligned, inside image data.
* No record anywhere carries a second size or a flag bit that could mean "compressed".

## Where the text is

The scan is disc-recon's heuristic made deterministic (`scan_text`: ≥ 3 glyph ids in
`1..0x4FF`, `0x8001` / `0x8002 <u16>` allowed, ended by `0x8000`, 2-aligned): 5,553 candidate
lines, every one inside a member. It is a heuristic — singletons inside TIM pixel data are
noise, and ids above `0x4FF` are not seen by it; the structural walk is `REC-03`'s job.

| where | candidate lines | note |
|---|---:|---|
| `M_FILES.BIN` map packs, **child 1** | 4,119 (+17 noise in child 6) | 373 of 555 maps carry text |
| `EV.BIN` event scripts | 1,341 | 248 of 265 |
| `HHON.OVL` | 58 | text inside a code overlay |
| everything else | 18 | 1–3 per member, inside image data — *hypothesis:* noise |

Map-pack child 1 has the family layout: `u32 n_tables; n × {u16 id, u16 length, u32 offset}`;
each table `u32 n; n × u32 offset`. In `M_A01000` the table ids are 4 and 906 and chain exactly
to the child's end.

**Duplication is heavy and every copy must be patched.** 5,553 lines are only 2,078 distinct
byte strings; 1,016 of those occur in more than one member. Within `M_FILES` 4,136 lines are
1,170 distinct strings (851 in ≥ 2 maps, one in 32). Maps come in variants sharing a 3-character
base (`M_A04000` / `M_A04001` / `M_A04100` …): of 87 bases with more than one text-bearing
variant, 50 have identical line sets in every variant and 37 differ. 247 strings occur both in a
map pack and in an `EV` script; 120 occur in more than one `EV` script.

**Also noticed, outside `BOKU.BIN`:** the same scan finds glyph-encoded text in the executable
itself — ~50 short lines around file `0x369D2` (RAM `0x800461D2`, many ending in the same glyph
`0x3E0`, *hypothesis:* a name list) and longer strings with ids up to `0x5CF` around file
`0x1A340` (RAM `0x80029B40`). disc-recon's "the executable's only Japanese is debug Shift-JIS"
was a Shift-JIS scan and does not cover these.

## Unknown

* `g_cd_dir + 0x14` (`0x800246AC`) and the dead pointer at `+0xC`.
* The `NIKKI.SEC` consumer and what the ids (0–100 with gaps) mean.
* Which code computes the index for the ten `file_load` sites whose index is not a constant
  (`0x8001DE78`, `0x80020E38`, `0x8003AD04`, `0x8003ADD0`, `0x8003AE88`, `0x800406B8`,
  `0x80040E10`, `0x80043C0C`, async `0x8001A0D0`) — presumably the `MI%02d` / `SBP` / `TOP*`
  families by base + n.
* PsyQ library function identities (`CdRead`, `CdReadSync`, `CdSearchFile`, `CdIntToPos`) are
  inferred from argument shape, not from signatures.
* The meaning of map names' digits and of `H` ids; all leaf formats marked `unknown`.
