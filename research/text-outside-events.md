# Text outside the event blocks (PLAN `REC-06`)

Everything a player can read that is **not** a message in an event block
([text-format.md](text-format.md)). Static analysis of `SCPS_100.88` and the seven `.OVL`
members; RAM addresses (file offset = RAM − `0x8000F800`; overlays at `0x80079A08`); our symbol
names, in [`symbols/loading.symbols.tsv`](symbols/loading.symbols.tsv). One row per array, with
proven bounds and no text: [`data/text-arrays.tsv`](data/text-arrays.tsv), regenerated by
`uv run --no-project --with capstone python work/rec06/mk_tsv.py --write`. How glyphs are
*drawn* (direction, spacing, the stepper) belongs to `research/text-renderer.md`; this file is
about where the words come from.

## Method: enumerate the readers, not the data

`REC-03` found arrays by scanning for glyph-shaped data and delimited the unterminated ones by
eye. Here the starting point is the code: **`glyph_draw` (`0x8002BA2C`) has 58 call sites**
(EXE 23, `TITLE` 28, `MUSI` 5, `HHON` 1, `TAKO` 1; `ZUKAN`, `BUMPER`, `ENDOTI` none; one more
through the wrapper `0x8002B9FC` from `HHON`), and every one was traced to the source of its
glyph argument. That source is one of four things: a walk over an array, an **immediate glyph
id in the instruction stream**, `0x34 + digit`, or a raw table indexed by code. The array
bounds in the TSV are then *derived*: each array is walked the way its reader walks it (item
count from the caller's index range, select line count from `g_select_lines`), and the walk's
end is compared with `REC-03`'s hand-typed end. **All 25 of `REC-03`'s ends are reproduced
exactly**, so that note's "delimited by hand" caveat is closed; its "reader untraced" caveat is
closed by the reader column.

*Limit:* this proves completeness for text drawn through `glyph_draw`. A routine that built
its own sprite from the font's texture page without calling `glyph_draw` would be invisible
here; the renderer trace is the cross-check.

  | `exe@8003D5F0` memory-card messages | 32 | `TITLE` `mc_msg_draw` `0x8007CB54` (and `0x8007CC4C`) | `g_mc_msg` (`TITLE` `0x800814C0`): 32 records `{n_lines, layout, line[3]}`; highest line used is 31 |

* **`ZUKAN` / `TAKO` / `MUSI` readers**: the three selects as above; `musi@2C` (32 move names)
  by `musi_move_draw` `0x80084F64` and `0x800850D8`, both inline line walkers.

  code knows their shape:

## Readers, for whoever changes the renderer

Array text does **not** funnel through one routine. Besides `dialog_draw`, `select_draw`,
`text_draw` (`0x800437F4`), `text_draw_h`, `text_nth` and `text_nth_line`
(text-format.md), there are **seven copies of an inline horizontal line walker** — `line_draw`
in the EXE, four in `TITLE` (`0x8007CB54`, `0x8007CC4C`, `0x8007FA94`, `0x80080680`), two in
`MUSI` — and `HHON` has its own vertical one (`hhon_entry_draw` `0x8007C278`: `x −= 14` at
`0x8001`, stop at `0x8000`). *Aliases:* [text-renderer.md](text-renderer.md) calls that same
function `hhon_text_draw_v` (its surface 3) and calls `number_draw2` below `number_draw_b`;
this file and `symbols/loading.symbols.tsv` use the first name of each pair. The horizontal walkers share three rules that are keyed on
**glyph ids**, which matters if the glyph table is rebuilt:

* glyph `0x0D` (the vertical long-vowel mark) is drawn as `0x0E` (the horizontal one);
* glyph `0x02` (`。`) is shifted 4 px left / down;
* the ids in `g_smallkana_ids` (`0x80036700`, 3 ids; the `TITLE` `0x80079BD4` and `MUSI`
  `0x8007A8B8` copies hold 4) are shifted 2 px — the small kana.

## Text made at run time

**There is no substitution.** No control code inserts a name, a number or an item; nothing
composes sentences. What exists:

* **Digits as glyphs, `0x34 + d`** (glyph `0x34` is `０`): `ant_msg_open` `0x80032030` writes
  three **random** digits (first 1–9) into words 1–3 of `exe@80029AFC` and opens it as a
  dialogue — the array is writable data, and its three cells are load-bearing. `TITLE`:
  `save_date_draw` `0x8007BB60` (month glyph `0x3C` = `８`, day digits), `file_rows_draw`
  `0x8007C8EC` (slot numbers), `extras_numbers_draw` `0x80080484` ("n ／ 3 1" and "n ％").
* **Labels as immediate glyph ids in code** — no data to extract; translating them is a code
  patch, and they are horizontal:

  | function | glyph ids | reads as | callers |
  |---|---|---|---|
  | `caught_label_draw` `0x80037544` | `0x21F 0x382`, `0x1B8`, `0x157` | caught, month, day | EXE, `HHON`, `MUSI` |
  | `specimen_label_draw` `0x80037698` | `0x3EC 0x158 0x1F7 0x25D`, `0x1B8`, `0x157` | specimen made, month, day | **none found — dead** |
  | `winloss_draw` `0x800377F8` | `0x26A`, `0x4B9` | wins, losses | EXE, `HHON`, `MUSI` ×2 |
  | `save_date_draw` (`TITLE`) | `0x3C`, `0x1B8`, `0x157` | 8, month, day | `TITLE` |
  | `file_rows_draw` (`TITLE`) | `0x5B0` ×4 sites | `）` after the slot number | `TITLE` |
  | `extras_numbers_draw` (`TITLE`) | `0x0F`, `0x37`, `0x35`, `0x28` (and `0x34`) | ／ 3 1 ％ | `TITLE` |

  `REC-04` had already marked 1209 (`0x4B9`) and 1456 (`0x5B0`) "used by code" in
  [`data/glyph-table.tsv`](data/glyph-table.tsv); this is where.
* **Numbers in the HUD and menus are sprites, not glyphs**: `number_draw` `0x800400F8` and
  `number_draw2` `0x800402D8` (52 call sites) build 8×12 sprites from a digit strip
  (`u = 0x48 + 8·d`). The clock, dates in lists, counts and scores need no translation.
* `dbg_printf` (`0x80022C38`, 100 call sites, ASCII formats such as `EVENT %d`) is the
  developers' 8×8 overlay. *Not determined:* which sites are reachable in the retail build. It
  is already English.

## Shift-JIS a player can see

A Shift-JIS scan of all eight code files finds exactly these strings:

| where | string | seen by a player? |
|---|---|---|
| `TITLE.OVL` `+0x188`…, through `g_save_title_parts` (`0x80081444`) and `g_save_title_digits` (`0x8008141C`) | the **memory-card save title**: `ボクの思い出` + slot + `　８月` + day + `日`, digits full-width, built by `save_title_build` (`0x8007AEF4`) into the `SC` header at `+4` | **yes — in the BIOS card manager.** 64 bytes of Shift-JIS; the BIOS wants full-width characters, so an English title is ≤ 32 full-width letters |
| EXE `0x800480C4` (+ English at `0x80048070`) | mod-chip warning | only on failure — [integrity.md](integrity.md) |
| EXE `0x80011738` | "event buffer over" | only if the `EV` buffer overflows — a developer panic that a careless reinsertion *can* trigger ([loading-and-memory.md](loading-and-memory.md)) |
| EXE `0x80029D94` | a debug assertion ("struct size is 0") | no |
| EXE `0x800722E8`–`0x80072670` | `PCload` / `PCsave` messages | **no — dead.** Their only users are `PCload` (`0x8005CD44`), called from the `g_pc_host` branches of `file_load`; `g_pc_host` (`0x80023830`) is `1` in the file, cleared by `sys_init`, and no code in any file sets it again |

`Krom2RawAdd` (the BIOS font) has two callers, both failure screens. **The "real failure path"
for card errors is glyph text**: `exe@8003D5F0`, drawn by `mc_msg_draw`.

## The picture diary

**The diary's prose is baked into the page images.** `ZUKAN.OVL` never calls `glyph_draw`; its
one array is the "write the diary and sleep?" select.

* A page is one 240×192 TIM in `NIKKI.BIN`, chosen by **page id**. `nikki_page_load`
  (`0x8007A280`) → `nikki_select(id)` (`0x8007A180`, the `NIKKI.SEC` consumer —
  loading-and-memory.md) → `file_load_async(149)`; `nikki_page_upload` (`0x8007A5BC`) puts it
  in VRAM at (896, 0).
* The id for a day is `g_diary_pages[day]` (`0x80046130`, `u8[31]`, part of the save). Tonight's
  id is `g_diary_today` (`0x8004612C`): event scripts propose pages through `diary_propose`
  (`0x80031CB0`), which keeps the page with the higher value in `g_diary_priority`
  (`0x80029890`, `u8[101]`); if nothing notable happened, `diary_pick_generic` (`0x80031B50`)
  takes the next unused id ≥ `0x48`, and the last day gets id 100 when every earlier page was
  generic. So `NIKKI.SEC`'s ids are **event-specific pages below `0x48` and a pool of generic
  pages from `0x48` up** (*the split is measured; which event proposes which page is
  `REC-05`'s*).
* The only thing composed at run time is the **date**: `nikki_date_upload` (`0x8007A53C`)
  uploads child `[day]` of `NIKKI_W.BIN` — a pack of per-day TIMs — next to the page. That is
  the "numerals missing" observation in [textures.md](textures.md).
* The desk behind it is `Z_A0n.BIN` before 19:00, `Z_N0n.BIN` after.

So the diary is wholly a texture job (README § "What gets translated", row 2): 94 pages plus
the date strips, no text arrays, no fragments.

## Line ids for these surfaces

`<file>@<original offset>.<item>` as proposed in text-format.md, with `<file>` ∈ `exe` (offset =
RAM address), `hhon`, `musi`, `tako`, `zukan`, `title` (offset = file offset); the TSV's
`line_id_prefix` column is the normative list. For a raw table the item is the row. A select is
one id. Two surfaces need a scheme the proposal lacks: immediates (`exe@code:80037544`,
`title@code:8007BB60` — the *function*, since the unit of translation is the label) and the
Shift-JIS title (`title@sjis:188`).
